`docs/engineering/Implementation/04-memory-system.md`: **Profile** (stable

### 2.2 Practical constraints this imposes on design

1. **No shared-model training on Gmail-derived content, ever** — deadline
   extraction must run as per-user personalized processing (in-workspace
   inference or provider call whose terms allow user-data processing without
   training). Eval for the Gmail pipeline must use **synthetic/consented email
   corpora, never real user mail** (§5).
2. **Extract-only + purpose-bound retention** is not just a privacy choice; it
   is a Google policy requirement (no permanent copies of user data). Confirm
   with counsel at P08 before OAuth verification.
3. **Job listings arrive via user action only** — reduces (not eliminates)
   reprocessing liability; keep per-user curated records small and user-visible.
4. **Eval sets may be hosted in-repo under their licenses** with attribution +
   checksums; CC BY-NC content is excluded from the product pipeline entirely
   (prior-run rule, re-affirmed).

## 4. Provenance rules (design now; runtime owned by P07/P12)

> These are the P02 design contract for provenance. Implementation, tests and
> restore/reconciliation proof are **`NOT_EXECUTED`** and owned by P07 (data
> architecture) and P12 (memory pipeline).

1. **Stable IDs:** UUIDs for all entities/records/workspaces (ADR-004); stable
   per-fact IDs with `workspace_id` isolation; no re-use of IDs across deletion.
2. **Versioned mappings:** every vector embedding carries `model_version`; every
   memory record carries schema version + source provenance; versioned
   prompt/chunking/embedding configs (prompt §3). **Never infer missing
   migration/memory values** — unknown → `needs_reflection` path, not guessing.
3. **Corrections/supersession history:** user corrections and consolidations are
   recorded events; merged-away content preserved in audit trail (engineering
   04); repeat-error metric (VB-07) measures whether corrections heal memory.
4. **Three lifecycle states distinguished:** (a) **primary deletion** — user
   request; (b) **backup expiry** — periodic/retention-driven removal of rotated
   copies, independent of user intent; (c) **legal hold** — freeze that
   overrides both. Design must never collapse these into one flag; P13 owns the
   implementation contract.
5. **Projection rebuild:** relational DB is authoritative; graph (AGE), vector
   (pgvector), search and cache projections are **derived and rebuildable** —
   rebuild job must be idempotent, workspace-scoped, and verifiable (row-count +
   content-coverage reconciliation, not just counts); deletion mirrors purge
   into every projection (M-08/M-09).
6. **Restore/reconciliation proof:** restore-from-backup and
   reconciliation-of-projections are P07/P12 acceptance items; this document
   only fixes the design requirements — evidence `NOT_EXECUTED`.

## 6. Data lifecycle for the cohort design-partner protocol

Carried from P01 evidence plan §4.3 (`SOURCE_DERIVED`) + prior-run
`04-regulatory-analysis` §1 (DPDP notice/consent design, `EXTERNAL_VERIFIED`
2026-08-07; force-status re-verify at P04 per UNK-P02-01):

1. **Consent-first onboarding:** pre-enrollment notice in plain language
   (English; regional-language option for tier-2/peri-urban), specifying what is
   collected, purpose (product validation), retention, deletion rights and
   withdrawal; **granular consent per data class** (documents, email metadata,
   telemetry); no dark patterns (DPDP §5/§6 design posture).
2. **Workspace-scoped only:** cohort data never cross-used; single-user
   isolation design; no cross-user memory (NG-05).
3. **Deletion on request:** user-initiated deletion purges system of record +
   vector/graph/search/cache projections; verified, timed purge exercise
   (M-08/M-09; VB-05); backup expiry and legal hold handled as separate states
   (§4.4). Export available to every participant.
4. **No PII in synthesis:** cohort data never enters eval sets or CI; telemetry
   is event counts only; synthetic generation is identity-free; any synthesis
   derived from cohort activity is consented, aggregate and reviewed.
5. **Measured > anecdotal:** cohort anecdotes are qualitative notes, never
   validation results alone (P01 §4.4 dual-channel rule).
6. **Professional legal review** before any compliance claim, including the DPDP
   notice wording and this lifecycle (RISK-P02-04; UNK-P02-01).
