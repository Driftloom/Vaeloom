## 1. Project Overview

### What Vaeloom Is

A personal AI career agent — a "second brain" for students and early-career
professionals (India, 18+, single-user). It ingests documents, builds structured
memory, and runs specialized agents to organize files, maintain resumes, search
jobs, and track deadlines. Suggest-mode-first: agents propose, user confirms.

### Design Source Docs

| Doc                                 | Purpose              | Key Claims                                                                                       |
| ----------------------------------- | -------------------- | ------------------------------------------------------------------------------------------------ |
| `docs/01-vaeloom-mvp-spec.md`       | MVP product spec     | 8 agents, 6 memory types, suggest-mode-first, approval gate                                      |
| `docs/02-system-architecture.md`    | 6-layer architecture | Interface → Connectors → Ingestion → Orchestration → Memory → Storage                            |
| `docs/03-agent-workflow.md`         | 10-step agent flow   | File upload → Organization → Memory → Resume → Job Search → ATS → Application → Outcome feedback |
| `docs/04-memory-knowledge-graph.md` | Memory system design | Knowledge graph + vector store + agentic RAG, 6 memory types                                     |

### Actual Tech Stack

| Layer    | Design Says           | Code Has                                                    |
| -------- | --------------------- | ----------------------------------------------------------- |
| Frontend | Web App               | Next.js 15 (`apps/web/`)                                    |
| Backend  | Core API              | FastAPI/Python (`apps/api/`)                                |
| Database | PostgreSQL + pgvector | PostgreSQL + pgvector (async SQLAlchemy)                    |
| Graph    | Knowledge graph       | Relational Entity/Relationship tables (Apache AGE NOT used) |
| Vector   | Semantic embeddings   | pgvector 1536-dim (OpenAI text-embedding-3-small)           |
| Cache    | Redis                 | Redis (for rate limiting)                                   |

## 7. RAG & Retrieval Verification

### Design Claim: "Agentic RAG — hybrid search (vector + keyword + graph traversal) with re-ranking"

**Source**: `docs/01-vaeloom-mvp-spec.md` §7.3

**Code Reality**: **CONFIRMED (simplified)**

**Three retrieval strategies** in `agents/memory_agent/retrieval.py`:

1. **Vector search** (lines 23-95): pgvector cosine distance
2. **Keyword search** (lines 126-179): SQL ILIKE on Entity and MemoryRecord
3. **Graph traversal** (lines 181-237): Find matching entities, follow
   Relationships to connected entities

**Hybrid mode** (lines 250-277): Combines all three, deduplicates, reranks.

**Reranker** (lines 239-248): Simple sort-by-`relevance_score` with dedup.
**Caveat**: Design says "Re-rank by relevance, recency, and confidence — newer
or more-confirmed facts outrank stale or single-source ones." Code only sorts by
score — no recency or confidence weighting.

## 8. Write Path Verification

### Design Claim: "Extract entities → dedup/merge → write to graph + vector store"

**Source**: `docs/01-vaeloom-mvp-spec.md` §7.4

**Code Reality**: **BROKEN**

**Step 1 — Extract**: `agents/memory_agent/extraction.py` — LLM-based entity
extraction. **WORKS**.

**Step 2 — Merge check**: `agents/memory_agent/merge.py` — Fuzzy string matching
(SequenceMatcher, threshold 0.8) against existing Entity records. **WORKS**.

**Step 3 — Write to graph + vector store**:
`agents/memory_agent/handler.py:43-86` — The `execute()` method returns
`"action": "suggest"` with entities, relationships, and merge_decisions. **NO
ACTUAL WRITE OPERATIONS**. The handler never calls any INSERT/UPDATE on Entity,
Relationship, or Embedding tables.

**File**: `apps/api/src/backend/agents/memory_agent/handler.py`

```python
# Lines 72-85 — returns suggestions, never writes
return {
    "agent_name": "memory",
    "action": "suggest",  # <-- always suggest, never execute
    "confidence": 0.85,
    "result": {
        "summary": f"Extracted {len(facts.entities)} entities...",
        "details": {
            "entities": [e.model_dump() for e in facts.entities],
            "relationships": [r.model_dump() for r in facts.relationships],
            "merge_decisions": merge_results,
        },
    },
}
```

**Critical Finding**: The entire memory extraction pipeline is a one-way street
— data goes in (extract + merge check) but never gets persisted to the graph or
vector store. The database models exist but nothing wires extraction output to
actual writes.

## 11. QA Gate Verification

### Design Claim: Agent output validation before delivery

**Code Reality**: **CONFIRMED**

**File**: `apps/api/src/backend/orchestrator/router.py:278-297`

```python
qa = QAAgent()
max_qa_retries = 3
for attempt in range(max_qa_retries):
    qa_result = await qa.validate(agent_output)
    if qa_result.decision == "approved":
        return agent_output
```

**QAAgent validation** (`agents/qa_agent/handler.py:32-80`):

1. Schema compliance (required keys: agent_name, action, confidence, result)
2. Hallucination check (looks for "[unsourced]" markers)
3. PII leak check (SSN, social security, credit card patterns)
4. Harmful content check (kill, hack into, illegal)
5. Confidence check (< 0.3 triggers rejection)

**Caveat**: Hallucination and harmful content checks are string-marker-based,
not semantic analysis.

## 21. Critical Findings

### Finding 1: Memory Write Path is Broken

The entire memory extraction pipeline extracts entities and checks for merges
but never writes them to the database. The `MemoryAgent.execute()` method
returns `"action": "suggest"` with extracted data, but no INSERT/UPDATE
operations exist. This means the core product value — "memory is the product" —
is not operational.

**Impact**: The knowledge graph and vector store are empty shells. No data flows
from extraction to persistence.

**File**: `apps/api/src/backend/agents/memory_agent/handler.py:72-85`

### Finding 2: Approval Gate is Bypassed

The approval infrastructure (database, service, API) is fully built, but the
orchestrator loop hardcodes `has_approval=False` for the ApplicationAgent,
bypassing the gate entirely. No other agent has approval gating in the loop.

**Impact**: The core trust mechanism ("suggest-mode-first, user confirms") is
not enforced. Agents can execute consequential actions without user consent.

**File**: `apps/api/src/backend/orchestrator/loop.py:83`

### Finding 3: Encryption at Rest is Not Implemented

The `encryption_key` is validated at startup but never used for actual
encryption. No `cryptography` library is imported. Database fields are stored in
plaintext. MinIO uploads use `use_ssl=False`.

**Impact**: All user data (documents, memories, credentials) is stored
unencrypted at rest and transmitted in plaintext.

**Files**: `services/encryption.py`, `services/storage_service.py:21`

### Finding 4: RLS is Inert

Row-Level Security policies exist in the database (migration 0005) but the
`TenantMiddleware` that would set the PostgreSQL GUCs (`app.tenant_id`,
`app.workspace_id`) is never mounted. The `set_rls_session_vars()` function is
never called.

**Impact**: Tenant isolation depends solely on application-level filtering. RLS
provides zero database-level protection.

**Files**: `middleware/tenant.py`, `main.py`

### Finding 5: 6 Enterprise Pages are 100% Mock

Admin, Billing, Organizations, Feature Flags, Marketplace, and Developer pages
contain hardcoded arrays with no API calls. The backend routers for these
features are fully implemented but the frontend doesn't use them.

**Impact**: Enterprise features appear to work in the UI but produce no real
data.

**Files**: `apps/web/src/app/workspace/[workspaceId]/admin/page.tsx`, etc.

## 23. Recommendations

### Priority 1: Fix the Memory Write Path

The Memory Agent must actually write extracted entities and relationships to the
Entity, Relationship, and Embedding tables. Without this, the entire product
value proposition is hollow.

### Priority 2: Wire the Approval Gate

The orchestrator loop must check `default_autonomy` and enforce approval for
`approval_gated` agents. The hardcoded `has_approval=False` must be replaced
with actual approval flow integration.

### Priority 3: Implement Encryption at Rest

Use the existing `encryption_key` with Fernet or AES to encrypt sensitive
database fields (password hashes, tokens, content) and enable S3 server-side
encryption.

### Priority 4: Mount TenantMiddleware

Add `TenantMiddleware` to the middleware stack in `main.py` so that
`set_rls_session_vars()` is called on every request, enabling RLS.

### Priority 5: Build Missing Frontend Features

- In-app document viewer (PDF/DOCX/image preview)
- Visual memory graph (D3/vis.js/cytoscape)
- Resume editor (form fields or rich text)

### Priority 6: Wire Enterprise Pages

Replace hardcoded mock data in Admin, Billing, Organizations, Feature Flags,
Marketplace, and Developer pages with real API calls to the existing backend
routers.

### Priority 7: Enable Monitoring

Uncomment Prometheus `/metrics` endpoint and OTel FastAPI auto-instrumentation
in `main.py`.

### Priority 8: Fix Security Gaps

- Mount IP Allowlist middleware
- Mount Audit middleware
- Add JWT audience/issuer validation
- Enable TLS for S3/MinIO
- Implement SAML signature validation
- Add missing security headers (X-XSS-Protection, Referrer-Policy,
  Permissions-Policy)
