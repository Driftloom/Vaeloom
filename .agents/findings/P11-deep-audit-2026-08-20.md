## FINDINGS

### P11-F001 — CRITICAL: SAML Signature Validation is Structural-Only in Practice

**File:** `apps/api/src/api/services/saml.py:77-127` **Severity:** CRITICAL
**Category:** Security

**What exists:**

- `_verify_signature_with_signxml()` (lines 28-74): Real cryptographic XML
  signature verification using signxml library. Requires `signxml` installed +
  `idp_certificate` provided.
- `_verify_signature_manual()` (lines 77-127): Structural-only fallback. Checks
  that `Signature`, `SignedInfo`, `SignatureValue`, `CanonicalizationMethod`,
  `SignatureMethod`, `Reference`, `DigestValue` elements exist. Does NOT verify
  any cryptographic values.

**The problem:** `signxml` is NOT in `pyproject.toml`. It's a lazy import via
`_signxml_available()` (line 20-25). In the default dev environment, signxml is
not installed. The code at line 206-210 falls through to
`_verify_signature_manual()`.

**OWASP SAML Security Cheat Sheet says:**

- "Validating the signature is necessary but not sufficient"
- "Always use local, trusted copies of schemas for validation"
- "Avoid signature-wrapping attacks"

**The structural fallback does NOT:**

- Verify the cryptographic digest matches the signed content
- Verify the signature value against the public key
- Protect against signature wrapping attacks
- Validate the canonicalization algorithm

**Impact:** An attacker can forge a SAML response with a structurally valid
`<ds:Signature>` element and bypass authentication entirely. The code at line
123 even logs:
`"SAML signature structure validated but NOT cryptographically verified"`.

**The `require_signature=True` default (line 141) is meaningful** — it rejects
assertions with NO signature element. But it does NOT reject assertions with a
structurally present but cryptographically invalid signature.

**Remediation required:**

1. Add `signxml` to `pyproject.toml` with version pin (>=4.0.4 to avoid
   CVE-2025-48994)
2. Make `idp_certificate` required when `require_signature=True`
3. Remove or gate the structural-only fallback behind a dev-only flag
4. Add assertion replay protection (nonce/InResponseTo tracking)

### P11-F002 — HIGH: Connector `config` Dict Stored in Plaintext

**File:** `apps/api/src/api/services/connector_ext_service.py:36,97`
**Severity:** HIGH **Category:** Security / Data Protection

**What P11 claims:** "connector credentials encrypted" **What's real:** Only
`token_ref` is encrypted via Fernet.

**The `config` dict** is stored as raw JSON (schema.py:155, `JSON` type). For
database connectors, this contains `connectionString` which typically includes
embedded passwords (e.g., `postgresql://user:password@host:5432/dbname`). For
REST/GraphQL connectors, it contains API URLs and potentially API keys in
headers.

**Per OWASP OAuth Cheat Sheet:** "Store tokens encrypted in a secure database...
use a strong encryption standard such as AES-256."

**Per Scalekit (2026):** "Encryption at rest protects your database. It does not
protect tokens that have been decrypted and loaded into runtime."

**Impact:** A database breach exposes all connector credentials in plaintext.
The `token_ref` encryption gives a false sense of comprehensive credential
protection.

**Remediation required:**

1. Identify which `config` fields contain sensitive values per connector type
2. Apply Fernet encryption to sensitive config fields (same pattern as
   `token_ref`)
3. Add a migration to encrypt existing plaintext config values
4. Update `get_decrypted()` to decrypt config fields on read

### P11-F003 — HIGH: `_decrypt_credential()` Silently Returns Raw Value on Failure

**File:** `apps/api/src/api/services/connector_ext_service.py:113-124`
**Severity:** HIGH **Category:** Security / Error Handling

**Code:**

```python
@staticmethod
def _decrypt_credential(ciphertext: str) -> str:
    if not ciphertext:
        return ciphertext
    if not is_encrypted(ciphertext):
        return ciphertext
    try:
        return decrypt_value(ciphertext)
    except Exception:
        return ciphertext  # <-- silently returns raw value
```

**Impact:** If the database is tampered with and the ciphertext is corrupted,
the raw corrupted value is passed as a credential to downstream services. A
malicious database admin could inject a crafted value that bypasses encryption
entirely — the `is_encrypted()` check on line 118 looks for the `gAAAAA` Fernet
prefix, so any value without that prefix is returned as-is.

**Remediation:** Raise an error on decryption failure instead of silently
returning the raw value. Log the failure for security monitoring.

### P11-F004 — HIGH: signxml CVE-2025-48994 (HMAC Algorithm Confusion)

**Severity:** HIGH **Category:** Supply Chain Security

**Source:** Vulert vulnerability database, disclosed 2026-07-07

**CVE-2025-48994:** signxml versions before 4.0.4 are vulnerable to HMAC
signature verification algorithm confusion attacks when X509 validation is
disabled (`require_x509=False`).

**Vaeloom mitigation:** The code uses `require_x509=True` (line 65), which
mitigates this specific CVE.

**But:** The library version is not pinned. If someone installs signxml < 4.0.4
and the code path changes to `require_x509=False`, the vulnerability becomes
exploitable.

**Remediation:** Pin `signxml>=4.0.4` in `pyproject.toml`.

### P11-F005 — MEDIUM: Webhook Secret Not Re-encrypted on Update

**File:** `apps/api/src/api/services/webhook_service.py:52-62` **Severity:**

If a new `secret` is passed in the update dict, it's stored unencrypted. The

### P11-F006 — MEDIUM: `ConsentState` TypeScript Type Mismatch

**File:** `apps/web/src/lib/api-client.ts:800-803` + `settings/page.tsx:68`
**Severity:** MEDIUM **Category:** Code Quality / Type Safety

**`api-client.ts` defines:**

```typescript
interface ConsentState {
  scopes: ConsentScope[];
}
```

**But `settings/page.tsx` casts:**

```typescript
res as unknown as {
  items?: Array<{ scope: string; revoked_at: string | null }>;

```

The backend returns `{ items: [...] }` not `{ scopes: [...] }`. The type is
never used correctly — double cast bypasses all type safety.

**Remediation:** Fix `ConsentState` interface to match actual API response
shape.

### P11-F007 — MEDIUM: 13 of 21 Agents Silently Fall to Fallback

**File:** `apps/api/src/api/orchestrator/loop.py:219-273` **Severity:** MEDIUM
**Category:** Architecture / Correctness

The dispatch chain is a hardcoded if/elif that handles: OrganizationAgent,
ResumeAgent, ATSAgent, JobSearchAgent, ApplicationAgent, GmailAgent, DriveAgent,
SchedulerAgent, MemoryAgent, MemoryHandlerAgent

The other 13 agents (Career, Learning, Research, GitHub, Coding, Reminder,
Analytics, Recommendation, Reflection, Security, Connector, Plugin) silently
return `agent.fallback()` results with no error logged to the user.

**Impact:** Users think these agents are working but they always return
fallback. No error message, no indication.

**Remediation:** Log a warning when an agent falls to fallback due to dispatch
mismatch. Consider making the dispatch dynamic via the agent registry.

### P11-F009 — LOW: All Infrastructure Components Are In-Memory

**Components affected:**

- Circuit breaker (`circuit_breaker.py`) — state dict in memory
- Rate limiter (`agent_limits.py`) — token buckets in memory
- Kill switch (`agent_observability.py`) — disabled set in memory
- Metrics collector (`agent_observability.py`) — records in memory
- Agent fallback policies (`agent_fallback.py`) — cache in memory

**Impact:** All reset on process restart. In a production deployment with
multiple workers or restarts, this means:

- Circuit breaker never trips (resets before threshold)
- Rate limits don't persist across restarts
- Kill switch settings are lost
- Metrics history is lost

**Note:** This is acceptable for MVP but must be addressed before production.

### P11-F010 — LOW: BaseAgent is a Skeleton (No Enforced Interface)

**File:** `apps/api/src/api/orchestrator/base.py` **Severity:** LOW
**Category:** Architecture

BaseAgent is 19 lines with:

- `mission`, `tools`, `memory_scopes`, `default_autonomy` (metadata only)
- `fallback()` — the only method, raises `NotImplementedError`
- No `execute()` contract — each agent defines its own signature
- `default_autonomy` is declared but never read by the orchestrator

**Impact:** No compile-time or runtime enforcement of the agent interface. The

### P11-F011 — LOW: Fallback Policies Exist But Are Not Integrated

**File:** `apps/api/src/api/infrastructure/agent_fallback.py` **Severity:** LOW
**Category:** Architecture

Four real fallback strategies exist:

1. `PrimaryWithFallback` — try primary, catch, try fallback
2. `RetryWithBackoff` — exponential backoff with jitter
3. `CachedFallback` — serve stale cache on failure
4. `ModelDowngradeFallback` — try cheaper model on failure

None are wired into the orchestrator loop. The loop calls `agent.fallback()`
directly (which raises `NotImplementedError` in the base class).
