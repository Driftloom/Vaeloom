=======================================

What 0069 changes
-----------------

1. recommendation_feedback gains a nullable workspace_id, deliberately not
   backfilled. The parent recommendations table has no workspace either, so any
   backfill would be a guess, and a guessed workspace is the contamination the
   column exists to prevent. Learning filters on an exact match, so a NULL row
   is quarantined and contributes nothing.

2. user_preference_vectors is keyed by (user_id, tenant_id, workspace_id). One
   vector was previously shared across every workspace a user belonged to.
   Legacy vectors are discarded, not migrated: they are derived data, and a
   primary key column cannot be NULL, so the old rows could not have been carried
   across at all. Each profile rebuilds on its next signal.

3. ck_memory_records_type_valid is dropped from memory_records. Its 24 literals
   are identical to the seeded career pack, so the domain-pack registry already
   speaks that table's language and the constraint was a second, separately
   maintained copy that could drift silently.

The rollback proof
------------------

The verification harness plants a row whose type comes from a temporary domain
pack, outside every frozen vocabulary, then rolls back. Observed on the passing
run: `alembic downgrade` exits 1 naming ck_memory_records_type_valid, and the
probe value.

This required widening the harness. With 0069 above 0068, `downgrade -1` alone
would have targeted only 0069 and never exercised the constraint 0068 reinstates.
The probe now seeds both memories and memory_records and the rollback spans two
revisions, so both vocabularies are proven to refuse. A probe that quietly stops
testing anything is the exact shape of bug this harness exists to catch.

Both migrations log the distinct types before restoring their CHECK, because
PostgreSQL reports a violated ADD CONSTRAINT as "violated by some row" with no
DETAIL. Measured, not assumed: on PostgreSQL 16 asyncpg's CheckViolationError
carries detail = None for this statement form, so the offending value never
reaches Python through the driver. The pre-restore log is what makes the refusal
both actionable for an operator and assertable here.


Defects found and fixed during this work
----------------------------------------

- 0069's primary key could not be taken against a populated table. A PK column
  is implicitly NOT NULL and every legacy vector is NULL, so `ADD CONSTRAINT ...
  PRIMARY KEY` would have failed against real data. It passed here only because
  the verification container's table is empty -- a defect that would have shipped
  green and failed on first contact with production. Now covered by two tests.
- document_service constructs MemoryRecord at two sites (612, 1761). The approved
  spec described the coupling as two-way; it is three-way. Dropping the CHECK
  couples to those sites as well as to import_memories.


What this does NOT prove
------------------------

- Concurrency during a real rollback window.
- Rollback against a large, production-shaped table. The probe is one row.
- Performance or behaviour at volume.

Seeded-data correctness only.


Operational note carried forward
--------------------------------

Rolling back 0069 after a second domain pack is deployed will refuse, because
memory_records will hold a type the reinstated frozen vocabulary does not list.
That is correct behaviour and matches 0068. The operational decision of what to
do then -- stop, or migrate the data forward first -- has to be made in advance,
not during an incident.

## Addendum: a privilege escalation this migration introduced, and closed

The first working version of 0069 created a workspace-scoped RLS policy BESIDE the
pre-existing user+tenant one. PostgreSQL ORs multiple PERMISSIVE policies for the
same command, so the effective predicate on recommendation_feedback became

    (user_id = me AND tenant_id = mine) OR (workspace_id = my_workspace)

The second branch names no user_id at all. Any member of a workspace could read,
update and insert every other member's rows, and because user_id is whatever the
caller supplies on INSERT, could file fabricated ratings in a victim's name. That
is a worse leak than the cross-workspace one 0069 was written to close, introduced
by closing it.

It shipped green because nothing tested for it: the existing policy test asserted
that a workspace policy *existed* and mentioned app.workspace_id, which a policy
sitting beside another one satisfies perfectly well. A test written to prevent the
defect was structurally unable to see it.

Fixed. 0069 now DROPS the pre-0069 policies instead of adding beside them, and its
own policy scopes on tenant AND workspace AND user -- workspace scoping answers
"whose workspace", not "whose row". Downgrade restores the replaced policies,
because a table left with no policy at all is an outage: RLS with zero policies
denies every row.

Verified against a live database: exactly one policy remains on each table, and it
reads app.user_id.

    recommendation_feedback | p_recommendation_feedback_workspace_isolation

Two new tests detect widening specifically: one asserts the pre-0069 policy is
gone, the other that the surviving policy reads app.user_id. The vacuous test that
claimed to cover the primary-key defect -- which asserted a result without ever
setting up the condition -- is replaced by one that asserts the ordering.

Three further defects in the same review, all of the shape "changed the schema,
did not change the behaviour it governs":

- POST /feedback never populated workspace_id, so every row stayed NULL and the
  quarantine was indistinguishable from "never recorded". Now threaded from
  authenticated context.
- The learning aggregate in ranking_weights still read WHERE user_id = :user_id.
  That is the actual cross-workspace leak, and it was left open in the one query
  that reads feedback -- the defect the entire migration exists to close. Now
  scoped by workspace, with legacy NULL rows excluded rather than counted
  everywhere.
- Two preference-vector upserts in approval.py omitted the column 0069 made NOT
  NULL and conflicted on a key it removed. Both raised; the second sat inside
  suppress(Exception) and the outer handler logged at debug. Approvals had quietly
  stopped updating preference vectors, with no error and no failing test.

Also fixed: POST /import never mapped MemoryTypeRejected, so an out-of-vocabulary
type escaped as a 500. It is 422 now, like create, update and supersede.

And a SQL error of my own, caught by the harness refusing to pass: CREATE POLICY
takes one parenthesised expression per clause, so `USING (a) AND (b)` parses as
`USING (a)` followed by stray `AND`. upgrade() wrapped it correctly; downgrade()
did not.

Final state: 50 live-PostgreSQL tests pass with 0 skipped, and pnpm verify:pg is
green across all nine steps.
